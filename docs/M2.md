# CrossLearn AI M2 — local working prototype

FastAPI and PostgreSQL now connect the teacher workspace to a complete pupil assessment flow. The frontend uses native JavaScript and the M1 visual design. All seeded accounts and learners are synthetic.

## Start and sign in

Double-click `crosslearn-ai/run-m2.cmd`, or run:

```powershell
cd P:\innovation\FOI2026\Agentic\crosslearn-ai\api
& ./.venv/Scripts/python.exe -m alembic upgrade head
& ./.venv/Scripts/python.exe -m app.seed
& ./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Open **http://127.0.0.1:8000/**. Stop with **Ctrl+C**. Port 8000 must be free; stop an existing instance first. PostgreSQL must be running. No frontend installation or build is needed.

Passwords are generated locally in **`api/.demo-access.json`**. Open that file locally and use the matching username/password. It is ignored by Git and outside the served directory. It is never sent to a model.

| Account | Scope |
| --- | --- |
| teacher.a | School A class, content approval, assignments, sessions, evidence and recommendation review |
| teacher.b | Independent School B class and records |
| researcher.a | Read School A evidence and export CSV; no classroom writes |
| admin.a | School A administration, teacher actions, export and audit |

Seeding is idempotent. Do not delete the credential file to change a password; an existing account's hash is not reset by seeding.

## Walkthrough

1. Sign in as `teacher.a`. Open **Content & approval**, expand the item details and review the keyed questions and scripts. Approve the version for **synthetic demo use**. This does not certify curriculum validity.
2. Under **My class**, assign the approved word set.
3. Open a learner, choose the assignment and **Start pupil session**. The teacher is signed out before handing the device to the pupil.
4. Solve 1 Down **ROOT**, 2 Across **MOSS**, 3 Across **STEM**. Click clues to select direction; type letters or use arrows/Backspace. Hints are logged separately from comprehension.
5. Answer six baseline questions without correctness feedback. Explore one text, one audio and one diagram explanation on different concepts. Answer six new post-test questions. All assessment questions offer the same read-aloud option; audio lessons have replay and accessible text.
6. Results come from server answer keys. Refresh resumes the server-held stage; only the pupil access token and crossword draft are stored in sessionStorage. Tokens expire after eight hours.
7. Choose **Teacher sign-in**, sign back in and open the learner. Inspect the evidence timeline, concept counts, percentage-point changes and exposure/accommodation logs.
8. Draft a recommendation, approve/edit/reject it and record feedback. Drafts and review history remain visible. Repeating the demo creates a new saved session and rotates the modalities.
9. Use `researcher.a` or `admin.a` for CSV export, and `admin.a` for audit history. The profile has withdrawal and deletion controls, with an explicit UI confirmation for deletion.

## Architecture and controls

One loopback FastAPI process serves `api/public` and `/api/*`. PostgreSQL stores school-scoped records. The standalone M1 modules and answer-key JSON are not publicly served. Staff content-review endpoints intentionally expose keys only to authenticated users in their own school.

Sign-in verifies Argon2 hashes. Opaque session tokens are stored as SHA-256 digests, expire in eight hours and are invalidated on logout. Cookies are HttpOnly for authentication, SameSite Strict, with a separate CSRF token verified against its server digest on writes. Foreign-Origin writes are denied. Local hostname restrictions reduce DNS-rebinding exposure. Application handlers do not log passwords, database URLs or tokens.

Teachers can access their assigned classes in their school. Researchers can read/export but cannot assign, analyze or review. Admins can perform school actions and view school audit history. Nested resources are checked through school/class authorization. Pupil credentials grant access to one assessment only.

The server owns `crossword → baseline → learn → post → results`. Explanations and correctness are omitted from baseline responses. Client score/correctness/learner-ID fields in answer submissions are ignored. PostgreSQL locks and unique constraints serialize writes, prevent duplicate marks, and reject conflicting retries with HTTP 409. Responses are never overwritten by the agent.

The default recommendation is a labelled **rule-based fallback**. Five bounded tools operate on an already-authorized snapshot: get learner evidence, compare trials, obtain approved explanations, draft a recommendation and propose a follow-up assessment. The follow-up remains reviewable text; no assignment is automatically published. Each run records input hash, model/source, error category and actual tool trace. Reviews append history rather than modifying original evidence.

## Optional server-only model

To use an already installed, approved Ollama model, configure `api/.env` and restart:

```dotenv
MODEL_PROVIDER=ollama
MODEL_ENDPOINT=http://127.0.0.1:11434/api/chat
MODEL_NAME=YOUR_INSTALLED_MODEL_TAG
MODEL_TIMEOUT_SECONDS=15
MODEL_API_KEY=
```

Default `MODEL_PROVIDER=none` needs no key, model or paid service. No model is downloaded automatically. The endpoint is operator configuration; pupil/model input cannot choose URLs. Redirects are disabled. The adapter requests a strict JSON schema, bounds output bytes/time and caps generated tokens. It follows the official [Ollama chat API](https://docs.ollama.com/api/chat).

At most one model call can choose `collect_more_evidence` or `revisit_concept` and eligible concept IDs. Extra fields, arbitrary tool calls, scores, labels and free prose are rejected. A proposed gap must match keyed post-test evidence. Final wording and numerical summaries come from deterministic templates. Missing provider, invalid output, network error and timeout produce fallback advice without changing marks.

Inputs contain at most 12 completed session summaries, format/exposure logs, content versions and approved scripts. No learner/school identifiers, pseudonyms, raw pupil text or teacher feedback enter the model. Repeated uncalibrated demo items always remain **INSUFFICIENT_EVIDENCE**, regardless of session count. Live billing telemetry and model-digest pinning remain future deployment work.

## CSV data dictionary

One row represents one concept in one completed session. Only researchers/admins can export authorized classes; withdrawn learners are excluded.

| Field | Meaning |
| --- | --- |
| learner_id / session_id | Random UUIDs; pseudonym omitted |
| content_version / rotation | Immutable seed version and zero-based demo rotation |
| concept / modality | Concept identifier and text/audio/visual condition |
| baseline_correct / baseline_total | Keyed baseline correct count and total (2) |
| post_correct / post_total | Keyed post-test correct count and total (2) |
| gain_pp | Post percentage minus baseline percentage, in percentage points |
| seconds | Elapsed lesson interval including interruptions; not attention |
| transcript / audio_played | Reported accommodation/playback request; not verified listening |
| read_aloud_count | Session-level count, repeated on each concept row |

## Retention and remaining limits

Only synthetic learners and participation states are seeded. There is no interface to enter child identities or claim real parental consent. Withdrawal blocks pupil access, new sessions and analysis. Deletion cascades through assessments, responses, model runs, recommendations and reviews. Audit retains actor/action/time without learner identifiers or educational payloads. Downloaded CSV files must be removed separately by their holder.

Synthetic records remain until deleted; no automatic retention job or backup service is provided. This local prototype is not ready for real child data. Institutional deployment requires managed identity, HTTPS/Secure cookies, shared rate limiting, monitoring, retention/backup policies, consent processes, security review and ethics/privacy approvals. The current password authentication and in-memory limiter support a single local process only.

General content editing/version creation, full localization, PWA offline sync and delayed retention belong to later milestones. The current content is an immutable seed with teacher demo approval. The frontend remains native JavaScript, not React. The earlier Sites project is the static M1 registration and does not host this FastAPI/PostgreSQL app.

Files: `api/app` backend; `api/migrations` schema revisions; `api/public` connected UI; `api/tests` tests; `api/requirements.lock.txt` tested dependency versions. Official reference: [FastAPI security](https://fastapi.tiangolo.com/tutorial/security/).
